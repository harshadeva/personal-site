03How I thinkSheet 03 / 10

Think first. Draw it. Then build it right.

Most failed projects don’t fail in the code. They fail because people imagined different things and found out too late. My process exists to close that gap before the first line of code, and to keep it closed while we build.

01 — Understand the problem, not just the request

Who uses this? What happens to the business if it breaks? What does “done” actually look like? I ask the uncomfortable questions on day one, so they don’t come up in week six.

Output → problem statement, user roles, constraints, risks

02 — Draw it and write it down

Flow diagrams, data models, sequence diagrams and a written scope. We go back and forth on paper until you, me and the team describe the project the same way. Changing a diagram takes minutes. Changing shipped code takes weeks.

Output → diagrams + scope document everyone has agreed to

03 — Slice the scope, then estimate

I break the work into small pieces that can each be delivered on their own, and estimate each one. Small pieces give honest estimates, and you can see exactly where the time goes.

Output → prioritized backlog with per-item estimates

04 — Build in short phases you can review

Agile, in short cycles. At the end of each phase you review working software, not a status report. If what’s being built starts drifting from what you expected, we catch it while it’s still cheap to fix.

Output → a working, reviewable build every phase

05 — Ship with guardrails

Code review, automated checks, CI/CD pipelines and static analysis on every change. Deployments should be boring, and I set them up that way on purpose.

Output → reviewed code, green pipeline, repeatable deploys

06 — Observe and improve

Logs, metrics and alerts from day one, so problems are spotted by monitoring and not by your customers. Then we improve based on real usage, not guesses.

Output → dashboards, alerts, a list of improvements backed by data

04PrinciplesSheet 04 / 10

Four rules I don’t bend, even when there’s a deadline.

  • SOLID

    Code that’s easy to change

    Each part does one job. New features extend the system instead of forcing a rewrite, so the tenth feature costs about the same as the first.

  • ACID

    Data you can trust

    Money and records move inside transactions: all or nothing, never half. No orphaned orders, no balances that don’t add up.

  • DRY

    One source of truth

    Each business rule lives in one place. When it changes, it changes once, and the bug can’t hide in a forgotten copy.

  • QUALITY > RUSH

    No borrowed time

    When the deadline is tight, I cut scope, not quality. Shortcuts aren’t free. You pay them back later, with interest.

    06LeadershipSheet 06 / 10

    Most disagreements are misunderstandings in disguise.

    When two people on a team disagree, I don’t pick a side over chat. I get both of them in the same room, at the same time.

    1. Same room. Everyone hears the same thing, at the same time.
    2. Same facts. First we agree on the problem and the scope.
    3. Then opinions. Each person makes their case, now about the same thing.

    Most of the time, the disagreement goes away once the scope is clear. When it doesn’t, it’s a real trade-off, and we decide it with data, not volume.
